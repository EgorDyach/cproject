## Задание 1–2. Подготовка таблицы и данных

```sql
CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    product_id  BIGINT NOT NULL,
    status      VARCHAR(20) NOT NULL,
    amount      NUMERIC(10, 2) NOT NULL,
    created_at  TIMESTAMP NOT NULL,
    updated_at  TIMESTAMP NOT NULL
);

INSERT INTO orders (user_id, product_id, status, amount, created_at, updated_at)
SELECT
    (random() * 100000)::BIGINT,
    (random() * 10000)::BIGINT,
    (ARRAY['NEW','PAID','DELIVERED','CANCELLED'])[floor(random() * 4 + 1)::INT],
    random() * 10000,
    NOW() - (random() * INTERVAL '2 years'),
    NOW()
FROM generate_series(1, 1000000);

ANALYZE orders;
```

Таблица создана по спецификации задания. Данные — 1 000 000 строк, `user_id` в диапазоне 0…100 000 (≈10 заказов на пользователя), `created_at` равномерно размазан по последним двум годам.

**В скрипте генерации из методички есть ошибка:**

```sql
(ARRAY['NEW','PAID','DELIVERED','CANCELLED'])[floor(random() * 4 + 1)]
```

`floor()` возвращает `double precision`, а индекс массива в PostgreSQL требует `integer`, поэтому запрос падает с ошибкой `array subscript must have type integer`. Исправлено приведением типа:

```sql
(ARRAY['NEW','PAID','DELIVERED','CANCELLED'])[floor(random() * 4 + 1)::INT]
```

Результат загрузки:

```
  rows   | heap_size | total_size
---------+-----------+------------
 1000000 | 85 MB     | 106 MB
```

После загрузки выполнен `ANALYZE orders` — без него планировщик работал бы по пустой статистике и строил заведомо неверные планы.

## Задание 3. EXPLAIN: план без выполнения

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 123;
```

```
 Gather  (cost=1000.00..17036.43 rows=11 width=53)
   Workers Planned: 2
   ->  Parallel Seq Scan on orders  (cost=0.00..16035.33 rows=5 width=53)
         Filter: (user_id = 123)
```

**1. Какой план выполнения выбрал PostgreSQL?**
Параллельное последовательное сканирование: два фоновых воркера (`Workers Planned: 2`) плюс лидирующий процесс читают таблицу кусками, а узел `Gather` собирает их результаты в один поток.

**2. Какой тип сканирования используется?**
`Parallel Seq Scan` — полный проход по всем 10 827 страницам таблицы. Индексов на момент выполнения не существует, альтернативы у планировщика нет.

**3. Как PostgreSQL планирует найти нужные строки?**
Прочитать каждую строку таблицы и применить к ней `Filter: (user_id = 123)`, отбросив всё, что не подходит. Оценка `rows=11` взята не из данных, а из статистики: планировщик знает число различных значений `user_id` (`n_distinct`) и делит на него общее число строк — 1 000 000 / ≈100 000 ≈ 10.

Обратите внимание: `cost=1000.00..17036.43` — это две разные величины. Первое число — стоимость до выдачи первой строки (у параллельного плана она ненулевая, потому что нужно запустить воркеры), второе — до выдачи последней. Единица измерения условная: за 1.0 принято чтение одной страницы последовательным доступом.

## Задание 4. EXPLAIN ANALYZE: план с фактическим выполнением

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 123;
```

```
 Gather  (cost=1000.00..17036.43 rows=11 width=53) (actual time=1.567..16.289 rows=6 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   Buffers: shared hit=10827
   ->  Parallel Seq Scan on orders  (cost=0.00..16035.33 rows=5 width=53) (actual time=7.026..11.545 rows=2 loops=3)
         Filter: (user_id = 123)
         Rows Removed by Filter: 333331
         Buffers: shared hit=10827
 Planning Time: 0.056 ms
 Execution Time: 16.318 ms
```

Что найдено в плане:

| Показатель | Значение | Что означает |
|---|---|---|
| Тип сканирования | `Parallel Seq Scan` | полный проход по таблице |
| Planning Time | 0.056 ms | время построения плана |
| Execution Time | 16.318 ms | реальное время выполнения |
| actual rows | 6 | сколько строк вернулось на самом деле |
| estimated rows | 11 | сколько ожидал планировщик |
| Rows Removed by Filter | 333 331 (на процесс) | ≈1 000 000 строк прочитано и выброшено |
| Buffers | shared hit=10827 | прочитано 10 827 страниц (85 MB) ради 6 строк |

**1. Чем EXPLAIN отличается от EXPLAIN ANALYZE?**
`EXPLAIN` только строит план и показывает оценки планировщика (`cost`, `rows`), запрос при этом не выполняется. `EXPLAIN ANALYZE` действительно выполняет запрос и добавляет к каждому узлу фактические данные: `actual time`, `actual rows`, `loops`. Практическое следствие: `EXPLAIN ANALYZE` над `INSERT`/`UPDATE`/`DELETE` реально изменит данные — такие запросы нужно оборачивать в `BEGIN … ROLLBACK`.

**2. Почему EXPLAIN ANALYZE может выполняться значительно дольше?**
Потому что он делает работу, а не оценивает её. Сверх этого добавляются накладные расходы на инструментирование: PostgreSQL снимает показания таймера при входе и выходе из каждого узла на каждой строке. На планах с миллионами строк это заметно искажает результат — при необходимости замеры делают с `EXPLAIN (ANALYZE, TIMING OFF)`.

**3. Чем отличаются estimated и actual rows?**
`estimated` — предсказание по статистике из `pg_statistic`, `actual` — факт. Здесь 11 против 6: расхождение почти в 2 раза, но для такого плана оно безобидно. Опасны расхождения на порядки — они означают, что статистика устарела (лечится `ANALYZE`) или что планировщик не учёл корреляцию колонок (лечится `CREATE STATISTICS`). Именно по разрыву `estimated`/`actual` в первую очередь и диагностируют плохие планы.

## Задание 5. Sequential Scan

**5a. Запрос без условия:**

```sql
EXPLAIN ANALYZE SELECT * FROM orders;
```

```
 Seq Scan on orders  (cost=0.00..20827.00 rows=1000000 width=53) (actual time=0.005..37.305 rows=1000000 loops=1)
 Execution Time: 57.753 ms
```

**5b. Запрос с условием, которое почти ничего не отсекает:**

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE amount > 0;
```

```
 Seq Scan on orders  (cost=0.00..23327.00 rows=999900 width=53) (actual time=0.004..57.745 rows=999999 loops=1)
   Filter: (amount > '0'::numeric)
   Rows Removed by Filter: 1
 Execution Time: 77.527 ms
```

**1. Какой тип сканирования используется?** `Seq Scan` в обоих случаях, причём здесь даже без распараллеливания — результат всё равно нужно отдать целиком, и параллелизм не окупается.

**2. Почему PostgreSQL выбирает Sequential Scan?**
В 5a условия нет вообще — нужны все строки, любой индекс был бы лишним посредником. В 5b условие формально есть, но под него подходит 999 999 строк из 1 000 000. Идти через индекс означало бы прочитать весь индекс, а потом всё равно прочитать всю таблицу — двойная работа.

Разница в `cost` показывает цену самого фильтра: 20827 против 23327. Дополнительные 2500 единиц — это `cpu_operator_cost` × 1 000 000 строк, то есть плата за вычисление `amount > 0` для каждой строки.

**3. Всегда ли Sequential Scan — плохое решение?**
Нет. Последовательное чтение диска в разы быстрее случайного, и когда нужна значительная доля таблицы, оно объективно выигрывает. `Seq Scan` — проблема только тогда, когда возвращается небольшая доля строк, а `Rows Removed by Filter` при этом огромен (как в задании 4: 6 строк на выходе против миллиона прочитанных).

> **Вывод.** Последовательное сканирование эффективнее индекса, когда: (а) выборка захватывает существенную часть таблицы (на нашем стенде — примерно с 50 % и выше, см. задание 8); (б) таблица настолько мала, что помещается в несколько страниц; (в) нужны все строки без фильтрации; (г) результат всё равно требует полного прохода — например, при агрегации по всей таблице.

## Задание 6. Первый B-tree индекс

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);   -- 9088 kB
ANALYZE orders;

-- тот же запрос, что и в заданиях 3-4
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 123;
```

```
 Bitmap Heap Scan on orders  (cost=4.51..47.60 rows=11 width=53) (actual time=0.006..0.008 rows=6 loops=1)
   Recheck Cond: (user_id = 123)
   Heap Blocks: exact=6
   Buffers: shared hit=9
   ->  Bitmap Index Scan on idx_orders_user_id  (cost=0.00..4.51 rows=11 width=0) (actual time=0.005..0.005 rows=6 loops=1)
         Index Cond: (user_id = 123)
         Buffers: shared hit=3
 Execution Time: 0.018 ms
```

### Сравнение «до» и «после»

| Метрика | До индекса | После индекса | Изменение |
|---|---|---|---|
| Тип Scan | Parallel Seq Scan | Bitmap Index Scan → Bitmap Heap Scan | — |
| Execution Time | 16.318 ms | **0.018 ms** | **быстрее в ≈900 раз** |
| Cost (итоговый) | 17 036.43 | 47.60 | в 358 раз меньше |
| Прочитано страниц (Buffers) | 10 827 | **9** | в 1200 раз меньше |
| Обработано строк | 1 000 000 (999 994 отброшено фильтром) | 6 | — |
| Rows Removed by Filter | 333 331 × 3 | 0 | фильтр не нужен |
| Используемый индекс | нет | `idx_orders_user_id` | — |

**1. Изменился ли план выполнения?** Да, полностью: вместо чтения всей таблицы тремя процессами — обращение к индексу и точечное чтение 6 страниц.

**2. Использует ли PostgreSQL созданный индекс?** Да. Условие переехало из `Filter` в `Index Cond` — принципиальная разница: `Filter` применяется к уже прочитанным строкам, `Index Cond` не даёт их прочитать.

**3. Насколько изменилось время?** С 16.3 мс до 0.018 мс. Но честнее смотреть на `Buffers`: 10 827 страниц против 9. Время зависит от кэша и загрузки машины, число страниц — нет, и именно оно определяет, как запрос поведёт себя под нагрузкой.

**Отдельное наблюдение.** Планировщик выбрал не `Index Scan`, а `Bitmap Index Scan` + `Bitmap Heap Scan`, хотя строк всего 6. Причина: эти 6 строк лежат в 6 разных страницах (`Heap Blocks: exact=6`), то есть каждое обращение к таблице — случайное чтение. Bitmap-план сначала собирает битовую карту нужных страниц, сортирует её по номеру страницы и читает таблицу по возрастанию адресов. Это превращает 6 случайных чтений в одно почти последовательное.

## Задание 7. Индекс есть, но используется не всегда

```sql
CREATE INDEX idx_orders_status ON orders(status);   -- 6848 kB
ANALYZE orders;

-- запрос повторён для каждого из четырёх значений
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'PAID';
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'NEW';
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'DELIVERED';
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'CANCELLED';
```

| Значение status | Строк | Доля таблицы | План | Execution Time |
|---|---|---|---|---|
| `PAID` | 250 360 | 25.04 % | Bitmap Heap Scan | 29.534 ms |
| `NEW` | 250 188 | 25.02 % | Bitmap Heap Scan | 27.407 ms |
| `DELIVERED` | 249 154 | 24.92 % | Bitmap Heap Scan | 26.590 ms |
| `CANCELLED` | 250 298 | 25.03 % | Bitmap Heap Scan | 27.078 ms |

**1. Во всех ли случаях PostgreSQL использует индекс?**
На этих данных — да, во всех четырёх. И это не совпадает с ожиданием, заложенным в задание. Причина в самих данных: генератор распределил статусы строго равномерно, по 25 % на каждое значение, поэтому «редкого» и «частого» статуса тут просто не существует. Чтобы всё-таки найти границу, при которой индекс перестаёт применяться, поставлен отдельный эксперимент — задание 8.

Важно и то, почему при 25 % индекс всё ещё выигрывает. Таблица целиком помещается в `shared_buffers` (85 MB против 128 MB), случайное чтение фактически бесплатно, а сам индекс по `status` компактный — 6.8 MB. Bitmap-план дополнительно сортирует страницы перед чтением, что убирает основной штраф индексного доступа. На реальном сервере с холодным кэшем и таблицей, не влезающей в память, та же самая выборка в 25 % почти наверняка ушла бы в `Seq Scan`.

**2. Почему PostgreSQL может выбрать Seq Scan при наличии индекса?**
Потому что решение принимается по стоимости, а не по факту существования индекса. Индексный доступ окупается, лишь пока число обращений к таблице невелико. Как только выборка покрывает значительную часть страниц, дешевле прочитать всё подряд.

**3. Как количество возвращаемых строк влияет на выбор плана?**
Прямо и решающе. Ключевая величина — не число строк, а число страниц, которые придётся тронуть. Достаточно сравнить два плана из этого прогона: при `user_id = 123` — `Heap Blocks: exact=6`, при `status = 'NEW'` — `Heap Blocks: exact=10827`, то есть **все** страницы таблицы. Во втором случае индекс уже не экономит ввод-вывод, он лишь добавляет к нему чтение самого индекса.

## Задание 8. Селективность

### Распределение данных

```sql
SELECT status,
       COUNT(*) AS rows,
       round(100.0 * COUNT(*) / SUM(COUNT(*)) OVER (), 2) AS pct_of_table
FROM orders
GROUP BY status
ORDER BY 2 DESC;
```

```
  status   |  rows  | pct_of_table
-----------+--------+--------------
 PAID      | 250360 |        25.04
 CANCELLED | 250298 |        25.03
 NEW       | 250188 |        25.02
 DELIVERED | 249154 |        24.92
```

### Зависимость плана от селективности

Чтобы найти точку переключения, к четырём равномерным статусам добавлены условия, дающие другие доли таблицы:

```sql
-- 8.1  высокая селективность
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 123;

-- 8.2  25 % таблицы
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'PAID';

-- 8.3  те же 25 %, но индексные планы запрещены вручную
SET enable_bitmapscan = off;
SET enable_indexscan  = off;
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'PAID';
RESET ALL;

-- 8.4  50 % таблицы
EXPLAIN ANALYZE SELECT * FROM orders WHERE status IN ('PAID','NEW');

-- 8.5  75 % таблицы
EXPLAIN ANALYZE SELECT * FROM orders WHERE status <> 'PAID';
```

| № | Условие | Строк | Доля таблицы | Выбранный план | Cost | Execution Time |
|---|---|---|---|---|---|---|
| 8.1 | `user_id = 123` | 6 | 0.0006 % | Bitmap Index Scan | 47.60 | **0.085 ms** |
| 8.2 | `status = 'PAID'` | 250 360 | 25.0 % | Bitmap Heap Scan | 16 760 | 26.793 ms |
| 8.3 | то же, индекс запрещён вручную | 250 360 | 25.0 % | Seq Scan | 23 327 | 44.502 ms |
| 8.4 | `status IN ('PAID','NEW')` | 500 548 | 50.1 % | Bitmap Heap Scan | 22 369 | 44.724 ms |
| 8.5 | `status <> 'PAID'` | 749 640 | 75.0 % | **Seq Scan** | 23 327 | 64.673 ms |

Строка 8.3 — проверка того, что планировщик не ошибается: при 25 % выборки индексный план действительно быстрее полного прохода (26.8 мс против 44.5 мс), и планировщик выбрал именно его.

Строки 8.4 и 8.5 показывают точку переключения. На 50 % таблицы индекс ещё выигрывает по стоимости (22 369 против 23 327), а на 75 % планировщик уже отказывается от него в пользу `Seq Scan`. Оценки при этом сходятся с фактом: 749 500 против 749 640 строк.

> **Вывод.** Эффективность индекса определяется не его наличием, а селективностью условия. Полезность падает монотонно: при долях порядка тысячных процента индекс даёт выигрыш в сотни раз (0.085 мс против 16 мс), в диапазоне единиц–десятков процентов выигрыш сокращается до полутора-двух раз, а после ≈50 % таблицы обращение к индексу становится чистыми накладными расходами. Физическая причина одна: чем больше строк подходит под условие, тем ближе число затронутых страниц к общему числу страниц таблицы — а как только они сравнялись, индекс уже ничего не экономит и лишь добавляет собственное чтение.

## Задание 9. Range Query по дате

**До создания индекса:**

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '7 days';
```

```
 Gather  (cost=1000.00..20062.37 rows=9437 width=53) (actual time=0.107..33.303 rows=9584 loops=1)
   ->  Parallel Seq Scan on orders
         Filter: (created_at > (now() - '7 days'::interval))
         Rows Removed by Filter: 330139
 Execution Time: 33.509 ms
```

**После создания индекса:**

```sql
CREATE INDEX idx_orders_created_at ON orders(created_at);   -- 21 MB
ANALYZE orders;

-- тот же запрос на четырёх диапазонах
EXPLAIN ANALYZE SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '1 day';

EXPLAIN ANALYZE SELECT * FROM orders WHERE created_at > NOW() - INTERVAL '1 year';
```

| Диапазон | Строк | Доля таблицы | План | Heap Blocks | Execution Time |
|---|---|---|---|---|---|
| 1 день | 1 401 | 0.140 % | Bitmap Heap Scan | 1 314 | **1.324 ms** |
| 7 дней | 9 584 | 0.958 % | Bitmap Heap Scan | 6 326 | **4.985 ms** |
| 1 месяц | 41 414 | 4.141 % | Bitmap Heap Scan | 10 602 | 13.429 ms |
| 1 год | 500 426 | 50.043 % | **Seq Scan** | — | 103.898 ms |

Для запроса из задания (7 дней) индекс дал ускорение с 33.5 мс до 5.0 мс — примерно в 6.7 раза.

**1. Во всех ли случаях используется индекс?**
Нет. На интервалах 1 день, 7 дней и 1 месяц — да, на интервале в 1 год планировщик вернулся к `Seq Scan`.

**2. Как размер диапазона влияет на план?**
Через долю таблицы, попадающую в диапазон. Здесь особенно наглядна колонка `Heap Blocks`: при однодневном интервале для 1 401 строки читается 1 314 страниц, при месячном — уже 10 602 страницы из 10 827 существующих. То есть на месячном интервале индекс формально ещё используется, но фактически заставляет прочитать 98 % таблицы. Заказы разбросаны по всей таблице случайно, физической кластеризации по дате нет — поэтому «мало строк» очень быстро превращается в «много страниц».

**3. Когда индекс становится невыгодным?**
Когда число страниц, которые придётся тронуть, приближается к размеру таблицы. На этих данных перелом наступает между 4 % и 50 % строк — примерно там, где `Heap Blocks` упирается в общее число страниц. Дальше индекс проигрывает вдвойне: он не сокращает чтение таблицы и требует прочитать себя.

## Задание 10. Bitmap Index Scan и Bitmap Heap Scan

**10.1. Выборка среднего объёма** (`status = 'NEW'`, 250 188 строк):

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'NEW';
```

```
   Recheck Cond: ((status)::text = 'NEW'::text)

   Buffers: shared hit=11040

```

Из `Buffers` видно распределение работы: 213 страниц — чтение индекса, остальные 10 827 — чтение таблицы.

```sql
-- 10.2  та же форма плана на выборке в 6 строк
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 123;

-- 10.3  выборка того же объёма, но индекса по amount нет
EXPLAIN ANALYZE SELECT * FROM orders WHERE amount BETWEEN 1000 AND 3000;
```

**10.2. Для сравнения, точечная выборка** (`user_id = 123`, 6 строк): `Heap Blocks: exact=6`, `Buffers: shared hit=9`, время 0.031 мс. Структура плана та же, объём работы отличается в тысячу раз.

**10.3. Выборка без подходящего индекса** (`amount BETWEEN 1000 AND 3000`, 199 947 строк, 20 % таблицы): индекса по `amount` нет, поэтому `Seq Scan`, 57.058 мс. Полезное сравнение с 10.1: похожая по объёму выборка с индексом отрабатывает вдвое быстрее (28.5 мс).

**10.4. BitmapAnd — пересечение двух индексов:**

```sql
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE user_id BETWEEN 1000 AND 2000
  AND created_at > NOW() - INTERVAL '1 month';
```

```
 Bitmap Heap Scan on orders  (cost=926.56..2295.58 rows=404 width=53) (actual time=2.717..3.038 rows=422 loops=1)
   Recheck Cond: ((user_id >= 1000) AND (user_id <= 2000) AND (created_at > (now() - '1 mon'::interval)))
   Heap Blocks: exact=412
   ->  BitmapAnd  (cost=926.56..926.56 rows=404 width=0) (actual time=2.682..2.682 rows=0 loops=1)
         ->  Bitmap Index Scan on idx_orders_user_id     (actual rows=9942 loops=1)
         ->  Bitmap Index Scan on idx_orders_created_at  (actual rows=41414 loops=1)
 Execution Time: 3.081 ms
```

Каждое условие по отдельности слабоселективно (9 942 и 41 414 строк), но их пересечение даёт всего 422 строки — и таблица читается всего в 412 страницах вместо 10 827.

**1. Что делает Bitmap Index Scan?**
Проходит по индексу и вместо того, чтобы сразу идти за каждой строкой в таблицу, строит в памяти битовую карту — отметки страниц (а если позволяет `work_mem`, то и конкретных строк внутри страниц), где лежат подходящие записи. Наружу он не отдаёт ни одной строки таблицы, поэтому в плане у него `width=0`.

**2. Что делает Bitmap Heap Scan?**
Получает готовую битовую карту, сортирует её по физическому порядку страниц и читает таблицу по возрастанию адресов. `Recheck Cond` в плане — обязательная перепроверка условия: при нехватке `work_mem` карта вырождается из построчной в постраничную (lossy), и тогда прочитанные страницы приходится фильтровать заново.

**3. Почему Bitmap Scan вместо обычного Index Scan?**
Обычный `Index Scan` идёт в таблицу за каждой найденной строкой в порядке индекса, то есть выполняет случайные чтения — и одну и ту же страницу может прочитать многократно, если в ней несколько подходящих строк. Bitmap-план каждую страницу читает ровно один раз и делает это последовательно. На выборках от нескольких десятков строк и выше это почти всегда выгоднее. Отсюда правило: `Index Scan` — для единиц строк и для запросов с `LIMIT`, где важна первая строка; `Bitmap Scan` — для средних выборок; `Seq Scan` — для больших.

## Итоги части 1

```sql
SELECT indexrelname AS index_name,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size,
       idx_scan AS times_used
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY indexrelname;
```

| Индекс | Размер | Назначение |
|---|---|---|
| `orders_pkey` | 21 MB | первичный ключ (создан автоматически) |
| `idx_orders_user_id` | 9 088 kB | точечный поиск по пользователю |
| `idx_orders_status` | 6 848 kB | выборка по статусу |
| `idx_orders_created_at` | 21 MB | диапазонные запросы по дате |

Итого: heap 85 MB, индексы 58 MB — служебные структуры уже составляют две трети объёма самих данных.

**Что показали измерения:**

1. Индекс даёт выигрыш там, где условие селективно. На `user_id = 123` (6 строк из миллиона) — ускорение почти в 900 раз и в 1200 раз меньше чтений.
2. Наличие индекса ничего не гарантирует. На выборке в 75 % таблицы планировщик игнорирует индекс и оказывается прав: `Seq Scan` там объективно дешевле.
3. Решает не число строк, а число страниц. `Heap Blocks` из задания 9 показывает это прямо: 41 414 строк (4 % таблицы) заставляют прочитать 10 602 страницы из 10 827 — почти всю таблицу.
4. `EXPLAIN` без `ANALYZE` показывает намерение, а не результат. Расхождение `estimated`/`actual` — основной диагностический признак: здесь оно составило 11 против 6, что нормально, но разрыв на порядки означал бы устаревшую статистику.
5. Bitmap-планы — не «промежуточный» вариант, а самостоятельный механизм: они превращают случайный доступ в последовательный и позволяют пересекать несколько индексов через `BitmapAnd`.
